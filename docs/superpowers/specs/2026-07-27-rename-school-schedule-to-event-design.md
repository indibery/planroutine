# `학교일정` → `행사` 용어 변경 — 설계

## 개요

항목 종류의 표시 이름을 `학교일정`에서 **`행사`**로 바꾼다. 그 결과 `EntryKind`가 들고 있던
두 라벨(`label` / `filterLabel`)의 분리 근거가 사라지므로 **하나로 합친다**.

DB 값(`kind = 'event'`)·스키마·마이그레이션은 **바뀌지 않는다.** 표시 문자열과 주석만이다.

## 배경 — 왜 지금 헷갈리는가

`일정`이 **우산말이자 라벨의 절반**으로 동시에 쓰인다.

```
시트 제목:    일정 수정 / 일정 추가     ← 우산말(모든 항목)
종류 세그먼트: [업무] [학교일정]         ← 라벨
목록 배지:    [업무] [일정]            ← 전부 일정인데 하나만 "일정"
일괄 pill:    일괄 일정 등록 N건
```

일정을 수정하는 화면에서 종류를 고르는데 그 선택지 하나가 또 "학교일정"이라, 우산말과 라벨이
겹쳐 읽힌다(사용자 신고, 2026-07-27).

`EntryKind`가 라벨을 둘 들고 있는 이유도 같은 뿌리다. 현재 주석이 이유를 적어뒀다.

> `label` — 배지·pill에 쓰는 짧은 라벨. 행마다 반복되므로 4글자 이내.
> `filterLabel` — 필터 칩·요약 줄에 쓰는 라벨. `일정`만 쓰면 업무와의 대비가 흐려진다.

**짧은 말이 약해서 긴 말을 따로 만든 것**이다. `행사`는 2글자인데도 강해서 그 분리가 필요 없다.

## 옛 규칙을 뒤집는다 — 그 우려는 실현되지 않는다

CLAUDE.md에 정반대 규칙이 있다.

> **일정 / 학교일정 / 업무**만 쓴다. "행사"·"행사표"는 쓰지 않는다(AI 프롬프트 본문 포함).
> 예외: `category_label.dart`의 `학교행사`는 에듀파인 실제 분류명이라 그대로 둔다.

우려는 명백히 **에듀파인 카테고리 `학교행사`와의 혼동**이었을 것이다. 확인 결과 **그 둘은 같은
행에 나타날 수 없다.**

- 카테고리 배지는 `schedule.category != null`일 때만 렌더된다(`schedule_tile.dart:132`).
- `category`를 채우는 것은 CSV 경로(`createFromImported`·`createBulkFromImported`)뿐이고,
  그 경로는 **항상 업무**다.
- 사진 AI 경로(= 행사)는 `registerAiSchedules`가 `category`를 아예 넣지 않는다.
- 캘린더 목록에는 카테고리 배지 자체가 없다.

따라서 `[행사]`(종류)와 `[학교행사]`(카테고리)의 공존은 구조적으로 불가능하다. 규칙을 뒤집되,
**왜 안전한지를 CLAUDE.md에 함께 남긴다** — 근거 없이 뒤집으면 다음 사람이 다시 되돌린다.

## 1. 표시 문자열

| 위치 | 지금 | 바꿈 |
|---|---|---|
| `ScheduleStrings.kindEvent` | `'학교일정'` | `'행사'` |
| `EntryKind.event.label` | `'일정'` | (합쳐짐 — 아래 §2) |
| `ScheduleStrings.bulkRegisterEvent(n)` | `'일괄 일정 등록 $n건'` | `'일괄 행사 등록 $n건'` |
| `ImportStrings.aiTitle` | `'학교일정을 사진으로'` | `'행사를 사진으로'` |
| `ImportStrings.heroTitle` | `'학교일정 사진으로 넣기'` | `'행사 사진으로 넣기'` |

`ScheduleStrings.kindTask`(`'업무'`)는 그대로다.

결과 화면:

```
종류 세그먼트: [업무] [행사]
목록 배지:    [업무] [행사]
일괄 pill:    일괄 행사 등록 N건
시트 제목:    일정 수정              ← 우산말 유지, 이제 충돌 없음
```

## 2. `EntryKind` — 라벨 두 개를 하나로

이름을 바꾸면 두 값이 **양쪽 종류 모두에서 같아진다**(`업무`=`업무`, `행사`=`행사`). 분리의
유일한 근거가 사라지므로 접는다.

```dart
enum EntryKind {
  /// 내가 처리할 일. 오늘 탭에 뜬다.
  task('task', ScheduleStrings.kindTask),

  /// 학교에서 열리는 일. 캘린더에만 보인다.
  event('event', ScheduleStrings.kindEvent);

  const EntryKind(this.dbValue, this.label);

  /// DB(`schedules.kind` / `calendar_events.kind`)에 저장되는 값. **바뀌지 않는다.**
  final String dbValue;

  /// 화면에 쓰는 이름. 배지·필터 칩·요약 줄이 모두 이 하나를 쓴다.
  /// 예전에는 짧은 `label`(`일정`)과 긴 `filterLabel`(`학교일정`)로 나뉘어 있었는데,
  /// 짧은 쪽이 우산말 `일정`과 겹쳐 약했기 때문이다. `행사`는 2글자로도 충분히 강해
  /// 분리가 필요 없다.
  final String label;
```

- `filterLabel` 필드를 없애고 **모든 사용처를 `label`로** 바꾼다. 현재 사용처:
  `filter_summary.dart:26`, `schedule_filter_bar.dart:237·243`, `event_edit_dialog.dart`의
  종류 세그먼트. (구현 시 `grep -rn "filterLabel" lib test`로 0건을 확인한다.)
- 문자열을 enum에 리터럴로 박지 않고 `ScheduleStrings`를 참조한다 — 지금 `label`이
  `'업무'`/`'일정'`을 하드코딩하고 있어 리포의 문자열 중앙화 규칙에서 벗어나 있었다.
  이번에 같이 바로잡는다.

## 3. 바꾸지 않는 것

**AI 프롬프트 본문**(`ai_schedule_parser.dart:131-139`):

```
첨부한 사진은 학교 월간·연간 일정표입니다. 표에 있는 모든 일정을 …
```

이것은 **소스 문서를 설명하는 말**이지 우리 분류가 아니다. AI가 읽을 종이의 실제 이름이
"월간 일정표"이고, 여기를 우리 UI 용어에 맞추면 추출 품질이 흔들릴 수 있다. 옛 규칙이 UI 용어와
AI 프롬프트를 한 줄로 묶은 것이 과했다 — **둘은 다른 청중을 향한다.**

**`category_label.dart:17`의 `학교행사`** — 에듀파인 실제 분류명.

**DB·모델·마이그레이션** — `kind` 값은 계속 `'task'`/`'event'`. 스키마 v8 그대로, 마이그레이션 없음.

**릴리즈 노트의 과거 항목** — 이미 출하된 문구는 그대로 두고, 이번 변경을 새 줄로 추가한다.

## 4. 주석·문서의 용어

`lib/` 안 주석 약 20곳이 `학교일정`을 쓴다(`entry_kind.dart`, `today_view.dart`,
`calendar_repository.dart`, `event_edit_dialog.dart`, `kind_badge.dart`,
`schedule_filter_bar.dart`, `ai_schedule_register.dart` 등). **함께 `행사`로 바꾼다** — 코드가
쓰는 말과 주석이 갈리면 다음 사람이 둘 중 어느 쪽이 맞는지 모른다.

단, `import_strings.dart:6`·`import_screen.dart:19`처럼 **"사진 AI 경로"를 설명하는 문장**은
문맥을 보고 자연스럽게 고친다(기계적 치환으로 문장이 어색해지면 다시 쓴다).

`docs/superpowers/specs/`·`plans/`의 **과거 문서는 손대지 않는다** — 그때의 결정 기록이다.

## 5. CLAUDE.md

「용어」 절을 뒤집는다.

- **일정 / 행사 / 업무**를 쓴다. `학교일정`은 더 이상 쓰지 않는다.
- **왜 `행사`가 안전한가**: 위 "옛 규칙을 뒤집는다" 절의 근거(카테고리 배지 렌더 조건 +
  경로별 종류 고정)를 한 줄로 남긴다.
- 예외 둘: `category_label.dart`의 `학교행사`(에듀파인 분류명), **AI 프롬프트 본문**(소스 문서
  설명이라 UI 용어와 분리).
- 「업무 / 학교일정 (EntryKind)」 절 제목과 본문의 용어, `label`/`filterLabel` 설명을 갱신.

## 테스트

**기존 테스트 17개 파일이 `학교일정`을 문자열로 쓴다.** 대부분 테스트 **이름**(한글 서술)이라
동작과 무관하지만, 용어 일관성을 위해 함께 고친다. 실제 어서션이 걸린 곳:

- `kind_badge_test.dart:29` — `'학교일정은 짧은 라벨 "일정"'` → 라벨 기대값 `'행사'`
- `filter_summary_test.dart:45` — `expect(summary(...), '검토 대기 21 · 학교일정')` → `'· 행사'`
- `schedule_tile_kind_badge_test.dart:31-46` — `EntryKind.*.label`을 쓰므로 값 변경에 자동 추종
  (수정 불필요, 통과 확인만)
- `entry_kind_test.dart:37-38` — `label.length <= 4` 어서션은 `행사`(2글자)로도 통과한다.
  다만 그 테스트의 근거 주석이 짧은/긴 라벨 분리를 전제하므로 **개정**한다.

**⚠️ 깨질 하드코딩 1곳** — `schedule_screen_input_test.dart:124`가 상수를 안 쓰고 리터럴을 쓴다.

문자열이 `일괄 행사 등록`으로 바뀌면 이 어서션은 **찾는 대상이 사라져 무조건 통과**한다 —

**E2E**(`integration_test/app_test.dart`) — `:627`은 `ScheduleStrings.bulkRegisterEvent(2)`를

문구)의 `학교일정`은 용어 일관성을 위해 고친다.

비어 있지 않고 `ScheduleStrings`와 일치하는지 확인하는 테스트를 `entry_kind_test.dart`에 둔다.

## 범위 밖 (YAGNI)

- DB `kind` 값 변경(`'event'` → `'party'` 같은) — 마이그레이션을 부를 이유가 없다.
- 우산말 `일정`을 다른 말로 바꾸기 — 충돌이 해소되면 `일정`은 우산말로 적절하다.
- `학사` 등 다른 후보로의 재검토 — 아래 근거 참고.
- 과거 스펙·계획 문서의 용어 소급 수정.

## 설계 근거

- **`행사`를 고른 이유**: 시험·방학이 "행사"인가 하는 의미상 걸림이 유일한 약점이고, `학사`가
  그쪽은 자연스럽다. 그러나 한국 학교에서 이 전체를 아우르는 관용어가 **"월중행사표"**라
  `행사`가 이미 그 역할을 한다. 교사에게 익숙한 쪽을 택했다(사용자 확인, 2026-07-27).
- **표시만 바꾸고 DB는 두는 이유**: `kind` 값은 사용자가 볼 일이 없고, 바꾸면 마이그레이션과
  기존 데이터 변환이 따라온다. 용어 문제는 표시 계층의 문제다.
- **라벨을 합치는 것이 이번에 딸려오는 이유**: 두 필드는 `일정`이라는 약한 단어를 보완하려고
  생긴 우발적 복잡도다. 원인이 사라졌는데 구조만 남기면, 다음 사람이 "왜 둘이지?"를 다시
  묻고 잘못된 쪽에 문자열을 추가한다.
