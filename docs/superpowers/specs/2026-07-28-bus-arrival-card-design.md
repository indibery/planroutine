# 버스 도착 카드 — 설계

## 개요

오늘 탭 최상단에 **출퇴근 버스 실시간 도착시간 카드**를 얹는다. 데이터는 TAGO(국가대중교통정보센터)
공공데이터이고, **앱이 TAGO를 직접 호출한다**(서버 없음).

정류장은 **출발지·도착지 2개 슬롯**만 갖고, 설정 탭에서 언제든 교체한다. 카드는 **기본 OFF**이고
켜지 않은 사용자의 화면은 1픽셀도 바뀌지 않는다.

프록시 서버는 **보류**다 — 지금 규모에서 값을 못 하고, 승격 조건을 §5에 명시했다.

기획 원본: 옵시디언 `60 프로젝트/플랜루틴(PlanRoutine)/공직플랜 버스 도착 기능 기획.md`

## 배경 — 왜 옵트인인가

이 앱의 목적축은 "매년 반복되는 교사 업무 사이클을 작년 데이터 기반으로 세팅"이다. 오늘 탭은
그 축의 끝단으로, 업무를 체크해 도장을 찍고 결산 링을 채우는 화면이다. **버스 도착은 그 축 밖의
정보**라, 상시 노출하면 화면의 주제가 둘이 된다.

그리고 이 앱은 화면 높이를 예산처럼 다룬다. 진행도 텍스트(`149 / 149 · 100% 완료`)를 지운 이유,
필터 칩을 접은 이유, 중요 배지를 인라인 ★로 바꾼 이유가 전부 픽셀 지출이었다. 카드는 약 80px을
쓴다 — 이 앱에서 작지 않은 지출이다.

그래서 **`설정 > 버스 도착 > 표시` 스위치 기본 OFF**로 두고, 켠 사람만 지출한다. 도장 모양 설정·
`SlideHintBar` 영구 닫기와 같은 계열의 결정이다.

## 기획 원본에서 뒤집은 것 3가지

원본 기획은 Laravel + MySQL + Redis + Sanctum 스택을 전제했다. 확인 결과 **공직플랜에는 백엔드가
없다**(`pubspec.yaml`은 sqflite 로컬 전용, `i_code/`에 Laravel 프로젝트 없음, 볼트의 Laravel 코드는
종료된 민원시스템). "기존 방식 재사용"할 대상이 존재하지 않는다.

### 1. 서버 DB + 로그인 → 서버 없음

원본은 `출발/도착 정류장 저장 → 서버 DB (기기 바꿔도 유지)`를 골랐다. 이 한 줄이 회원가입·로그인·
Sanctum 토큰·계정 삭제 기능(App Store 심사 필수)을 전부 끌고 온다. **지금 공직플랜은 로그인이
없는 앱**이다.

게다가 일관성이 안 맞는다 — 기기를 바꾸면 일정·이벤트가 **이미 전부 사라진다**(sqflite 로컬 전용).
정류장 2개만 클라우드에 두는 것은 앱의 나머지와 어긋난다.

정류장을 `shared_preferences`에 둔다. **대가**: 기기 교체 시 정류장 2개를 다시 등록해야 한다(수용).

원본이 서버를 둔 나머지 이유(인증키 은닉·호출량 통제)는 프록시만으로 충족되고 로그인이 필요 없지만,
그 프록시조차 지금 규모에서는 값을 못 한다 — §2에서 다룬다.

### 2. 두 정류장 항상 표시 → 지금 방향만 + 토글

원본 스케치는 출근·퇴근 정류장을 항상 같이 보여준다. 그러나 **아침 7시 32분에 학교앞 정류장의
실시간 도착시간은 쓸모가 없다.** 실시간 정보의 유효기간은 몇 분뿐이고 퇴근은 8시간 뒤다.

| | 둘 다 표시 | 지금 방향만 |
|---|---|---|
| 오늘 탭 화면 지출 | ~140px | **~80px** |
| TAGO 점유 정류장 | 2개 | **1개** |
| 한도상 동시 사용자 | 약 250명 | **약 500명** |

한도 계산 근거: 서버 캐시가 없으니 **폴링 주기가 곧 호출 주기**다. 정류장 1개 × (5분 관측 / 30초
폴링) = 10 호출, 출퇴근 왕복 2회면 20 호출/일/명. 개발계정 10,000/일 ÷ 20 = 500명. 정류장을
2개 점유하면 절반이 된다. (운영계정 승격 시 10배.)

쓸모없는 정보를 지우면 화면 예산과 호출 예산이 **동시에** 절반이 된다. 지난 항목을 롤링 7일로
자르고 기본 접은 것과 같은 규율이다.

그 결과 원본 6번의 ⭐ 항목 "시간대별 출근/퇴근 자동 전환"의 의미가 바뀐다 — 순서를 뒤바꾸는 게
아니라 **어느 정류장을 폴링할지 고르는 스위치**가 된다. 로직은 더 단순하고 효과는 더 크다.

계산의 전제("1인이 한 번에 5분 관측")는 **낙관적이다** — 카드를 켜둔 채 오늘 탭에 더 오래
머무를 수 있다. §1의 시간대와 접기가 그 낙관에 상한을 준다: 시간대 밖이면 접힌 채 폴링하지 않고,
아침에 접으면 퇴근 시간대까지 호출이 0이다. 상한이 UI에 있다는 것은 사용자가 스스로 예산을 줄일
수단을 갖는다는 뜻이다.

### 3. 신호등 3색 → 색을 쓰지 않는 기본값 + 색을 쓰는 선택지

원본은 `3분↓ 빨강 / 3~7분 노랑 / 그 이상 초록`이다. 색만 쓰면 이 팔레트와 충돌한다 —
노랑은 골드와 물리적으로 구별되지 않고, 현재 색 규칙은 이미 포화 상태다
(`골드=오늘·중요` / `붉은색=공휴일·일요일` / `파랑=토요일·이벤트`).

**해법을 하나로 고르지 않고 설정으로 나눴다.**

- 기본 `간단히`는 **새 색을 하나도 쓰지 않는다.** 임박을 굵기·크기로 낸다. 팔레트 충돌 문제와
  라이트 모드 노랑 문제가 **기본 경험에서 완전히 사라진다.**
- 선택지 `시간 축`만 3색을 쓴다. 여기서는 **축 위 위치가 색의 문맥을 준다** — 왼쪽 점이
  빨강인 것은 "공휴일 빨강"으로 읽히지 않는다. 형태가 색의 문법을 지정하는 것은 CLAUDE.md가
  ★를 남긴 논리("남은 신호 셋이 전부 색이라 형태가 마지막 비색상 단서다")와 같다.

즉 **색의 비용을 감당할 사람만 감당한다.** 검토 과정에서 3구 신호등 안(색·위치 두 채널)도 만들어
비교했는데, 신호가 가장 강한 대신 가장 높고(≈92px) 색을 반드시 들여야 해서 채택하지 않았다.

## 1. 카드 UI

### 카드 모양은 설정으로 고른다 — 두 가지

`설정 > 버스 도착 > 카드 모양`에서 **간단히**(기본) / **시간 축** 중 고른다. `완료 도장 모양`이
이미 같은 구조다 — `SealStyle` enum이 모양 규칙(`isSquare`·`usesIcon`)을 들고 위젯은 enum만
보고 그린다. `BusCardStyle`도 같게 만든다.

```
간단히 (기본) — 펼침 ~60px
┌───────────────────────────────────┐
│ 🏠→🏫 출근 · 시청앞   07:32 기준 ⌃ │  ← 제목줄 전체가 접기/펼치기
│ 720번 2분   150번 5분   15번 11분  │
│  [ 퇴근 보기 ⌄ ]                   │
└───────────────────────────────────┘

시간 축 — 펼침 ~80px
┌───────────────────────────────────┐
│ 🏠→🏫 출근 · 시청앞   07:32 기준 ⌃ │
│ 지금      5분     10분      15분   │
│ ├──●───────●─────────────●─────┤   │
│    720     150            15       │
│  [ 퇴근 보기 ⌄ ]                   │
└───────────────────────────────────┘

접힘 (두 모양 공통) ~42px
┌───────────────────────────────────┐
│ 🏠→🏫 출근 · 시청앞              ⌄ │  ← 같은 칸, 같은 자리
└───────────────────────────────────┘
```

**기본이 `간단히`인 이유**: 새 색 토큰이 0개고, 가장 낮고, **노선 수·배차 간격 어떤 조건에서도
깨지지 않는다.** 이 앱은 늘 조용한 쪽을 기본값으로 두었다 — 카드 자체가 기본 OFF, 필터 기본 접힘,
지난 항목 기본 접힘. 같은 규율이다.

임박은 색이 아니라 **굵기·크기**로 낸다(3분 미만만 `ink` + `w800 18px`, 나머지 `sub` + `w600 14px`).
요일 헤더를 `본문색 + w700`으로 해결한 것과 같은 수법이다.

**`시간 축`은 조건부다.** 간격이 공간으로 보여 "이거 놓치면 6분 더"가 숫자 없이 읽히는 대신,
두 버스가 3분 안으로 붙으면 점과 라벨이 겹치고 15분 넘는 버스는 오른쪽 끝에 몰린다. 조건이 맞는
사람이 고르는 것이라 기본값이 아니다. 축 위 점 위치가 색의 문맥을 주므로 신호 3색을 여기서만 쓴다.

- 축 범위는 0~15분, 위치는 3~97%로 clamp한다 — 양 끝에서 점이 반쯤 잘리지 않게.
- `07:32 기준`은 마지막 조회 시각이다 (§2 경과 보정 참조).
- 방향 토글은 **화면 수명**이다. 누르면 그 화면이 살아있는 동안 유지되고 저장하지 않는다.
- **두 모양은 실패 계약(§3)·접기·시간대를 전부 공유한다.** 다른 것은 본문 렌더뿐이다.

### 몇 개까지 보여주나 — 필터를 걸었는지에 따라 다르다

실측하니 정류장 하나에 노선이 5개였다(축약 후). 사용자는 §4의 확인 시트에서 타는 노선만
고를 수 있으므로, 상한 규칙을 **그 선택을 존중하는 쪽으로** 나눈다.

| `routeIds` | 표시 |
|---|---|
| 비어 있음 (전부) | 가장 빠른 **3개** + `N개 더` 한 줄. 탭하면 전체 |
| 골라둠 | **전부 표시.** 자기가 고른 것을 자르지 않는다 |

필터를 걸었다는 것은 "이것들이 내 버스다"라는 뜻이므로 자르면 안 된다. 안 걸었다는 것은
"아무거나"라는 뜻이니 빠른 것 위주로 충분하다. 3이라는 수는 월 그리드가 이벤트 점을 3개로
자르는 것과 같은 값이다.

### 접기는 제목줄에서, 접어도 제목줄은 제자리

**접기와 펼치기가 같은 칸이어야 한다.** 접기를 카드 하단에, 펼치기를 접힌 줄에 두면 누를 때마다
표적이 위아래로 움직인다.

그래서 **제목줄 전체를 탭 대상으로 삼고 chevron을 오른쪽 끝에 고정**한다. 접으면 본문과 하단만
사라지고 제목줄·컨테이너는 제자리다 — 같은 칸에서 계속 토글된다.

이 구조는 이 앱에 이미 있다: `_overdueHeader`(`기한이 지난`)가 라벨 + `Spacer()` + 오른쪽 끝
chevron이고 줄 전체가 `HitTestBehavior.opaque` 탭 대상이다. **접힌 상태를 별도 pill로 만들지
않는 이유**도 여기다 — 컨테이너가 모양을 바꾸면 제목줄이 미묘하게 이동해 "같은 칸"이 깨진다.

접었을 때 사라지는 것과 남는 것:

| | 접힘 |
|---|---|
| 도착 분 (`720번 2분`) | **사라진다** — 안 보이게 하는 것이 목적이다 |
| 기준시각 (`07:32 기준`) | **사라진다** — 폴링을 멈추니 신선도를 말할 근거가 없다 |
| 방향 토글 (`퇴근 보기`) | 사라진다 — 접힌 상태에서 방향을 고를 이유가 없다 |
| 방향·정류장 (`🏠→🏫 출근 · 시청앞`) | 남는다 — 무엇이 접혀 있는지는 알아야 한다 |

- **접힘 = 폴링 정지.** 화면 예산과 호출 예산을 동시에 줄인다.

### 시간대가 방향과 펼침을 정한다

설정에 **출근 시간대 / 퇴근 시간대** 두 줄을 둔다. 기본값은 교사 일과 기준
`07:00–08:30` / `16:00–18:00`이고 사용자가 바꾼다.

**용어** — 이 문서에서 `시간대 안` / `시간대 밖`은 **지금 시각이 그 두 구간 중 하나에 들어 있는지**를
뜻한다. 설정 화면의 낱말(`출근 시간대`)과 같은 말을 쓴다.

```
00:00 ──────── 07:00 ════════ 08:30 ──────── 16:00 ════════ 18:00 ──────── 24:00
      시간대 밖        출근 시간대      시간대 밖       퇴근 시간대      시간대 밖
        접힘             펼침            접힘            펼침            접힘
        요청 0          30초 폴링        요청 0         30초 폴링        요청 0
                                    ↑ 일과시간(9~16시)이 여기
```

- **접기는 ═ 에서만 눌린다** — 거기서는 펼쳐져 있다.
- **펼치기는 ─ 에서만 눌린다** — 거기서는 접혀 있다.

이 비대칭이 아래 override 수명 규칙의 근거다.

**이 시간대가 정오 고정 상수를 대체한다.** 시간대가 방향까지 정하므로 별도 전환 시각이 필요 없다 —
설정은 두 줄 늘지만 상수 하나가 사라져 실질 복잡도는 비슷하다.

```
resolveBusDisplay(now, windows, override) → (direction, expanded)

시간대 안        → 그 시간대의 방향, expanded = true
시간대 밖        → 다음에 올 시간대의 방향, expanded = false
override 유효 → expanded를 덮는다
```

시간대 밖에서 **다음에 올 시간대**의 방향을 쓰는 이유: 밤 9시에 보여줄 것은 내일 출근 버스이고, 오전
10시에 보여줄 것은 오늘 퇴근 버스다. "다음에 탈 버스"가 사용자가 궁금한 것이다.

### 시간대 밖에서도 사라지지 않는다 — 접힌 채로 남는다

시간대 방식의 실패 모드는 명백하다: **늦은 날 8시 35분에, 정확히 가장 필요한 순간 카드가 없다.**
그래서 시간대 밖에서는 숨기지 않고 **접힌 상태로** 남긴다. 제목줄을 탭하면 펼쳐진다.

이 결정이 세 상태(시간대 안 / 시간대 밖 / 수동 접기)를 **펼침·접힘 한 축**으로 통합한다. 시간대는 그 축의
기본값을 자동으로 정하는 것이고, 사용자의 탭은 그 기본값을 덮는 것이다.

### override 수명 — 접기와 펼치기는 뜻이 달라 수명도 다르다

`shared_preferences`에 `overrideAt`(ISO)과 `overrideExpanded`(bool)를 저장한다.

| 행동 | 언제 눌리나 | 수명 | 왜 |
|---|---|---|---|
| **접기** | 시간대 안에서만 (시간대 밖은 이미 접힘) | **그 시간대가 끝날 때까지** | "오늘 아침 볼일 끝" — 남은 시간대 동안 다시 뜨면 접은 뜻이 없다 |
| **펼치기** | 시간대 밖에서만 (시간대 안은 이미 펼침) | **30분** | "지금 잠깐 예외로 필요" — 예외는 예외답게 짧아야 한다 |

**같은 수명을 주면 둘 중 하나가 반드시 틀린다.** 접기를 30분으로 하면 아침에 접어도 30분 뒤 다시
뜬다. 펼치기를 시간대 끝까지로 하면 늦은 날 8시 35분에 펼친 카드가 **일과시간 7시간 내내 펼쳐진 채
폴링한다**(사용자 지적, 2026-07-28). 겉보기에 같은 토글이지만 뜻이 다르므로 수명도 다르다.

### 일과시간 자동 접기는 별도 설정이 아니라 파생이다

"일과시간(9시~16시)에는 자동으로 접혀 있어야 한다"는 요구는 **위 표만으로 충족된다.**

- 9시~16시는 두 시간대 사이 = 시간대 밖 = 이미 접힘.
- 유일한 누수였던 늦은 날 override가 30분으로 끊긴다: 기본 출근 시간대 종료 `08:30 + 30분 = 09:00`.

별도로 `일과시간` 시간대를 설정에 두지 않는다 — 출퇴근 시간대와 **어긋날 수 있다.** 출근 시간대를
`07:30–09:00`으로 바꾸고 일과시간을 그대로 두면 두 설정이 겹치고, 어느 쪽이 이기는지 사용자가
알 수 없다. 시간대에서 파생시키면 시간대를 바꿀 때 자동으로 따라온다.

### override는 시간대 판정과 반대일 때만 저장된다

접기·펼치기가 각자 한쪽 상황에서만 눌리므로 규칙이 단순해진다.

```
탭 → 지금 펼침이면 접기, 접힘이면 펼치기

접기:   시간대 안 → override = collapsed (그 시간대가 끝날 때까지)
        시간대 밖 → override 삭제 (기본값이 이미 접힘)
펼치기: 시간대 밖 → override = expanded (30분)
        시간대 안 → override 삭제 (기본값이 이미 펼침)
```

즉 **override는 항상 "시간대 판정의 반대"만 담는다.** 같은 방향이면 저장할 이유가 없어 지운다.
상태가 스스로 정리되므로 "하루를 시간대들이 나눈 4조각" 같은 구간 개념이 필요 없다 — 앞선 리비전이
그 개념을 두었는데, 접기·펼치기의 수명을 갈라놓자 사라졌다.

### 시간대 설정의 기본값과 검증

- 기본값 `출근 07:00–08:30` / `퇴근 16:00–18:00`. 퇴근 시간대 시작을 15:30에서 **16:00으로
  옮겼다** — 일과시간이 16시까지라는 실사용 기준(사용자, 2026-07-28)에 맞춘다.
- 시작 < 종료여야 한다. 자정을 넘는 시간대는 지원하지 않는다.
- 두 시간대가 겹치면 저장을 거부한다 — 겹치면 방향 판정이 모호해진다.

### 색 토큰 — `시간 축`에서만 쓰인다

`AppColors`에 4개를 **추가**한다(기존 값 변경 없음). 다크·라이트 두 `_Palette`에 모두 넣는다.

| 토큰 | 다크 | 라이트 | 용도 |
|---|---|---|---|
| `busSignalNear` | `#EF5F52` | `#CF3A2A` | 3분 미만 점 |
| `busSignalSoon` | `#F2B23C` | `#C98A0E` | 3~7분 점 |
| `busSignalFar` | `#5FC98A` | `#1E9E63` | 7분 초과 점 |
| `busSignalOff` | `#33F0EAD9` | `#D4DBE6` | 축 레일 |

**기본값(`간단히`)은 이 토큰을 하나도 쓰지 않는다.** 켜지 않은 사용자와 `간단히`를 쓰는 사용자에게
팔레트는 지금과 완전히 같다.

이름에 `bus`를 박는 이유가 있다. 이 색들은 **시간 축 위에서만** 유효하다 — 다른 곳에서
`busSignalSoon`을 강조색으로 갖다 쓰면 위에서 회피한 팔레트 붕괴가 그때 일어난다. 이름이 오용을
막는다.

라이트의 노랑은 흰 배경 대비가 없어 딥 앰버(`#C98A0E`)로 잡는다. 이 값은 라이트 `gold`(`#9A7415`)와
색상이 인접하다 — 축 위 위치가 문맥을 주므로 수용하되, **실기기에서 확인할 항목**으로 남긴다.
다만 기본값이 `간단히`라 이 위험은 **`시간 축`을 고른 사람에게만** 온다.

점은 카드 배경색으로 2px 테두리를 둘러 축 레일과 겹칠 때 형태가 유지되게 한다.

## 2. 아키텍처 — 앱이 TAGO를 직접 호출한다

```
[Flutter: features/bus/]
  shared_preferences  정류장 2슬롯 + 도시코드 + ON/OFF
  TAGO 키             --dart-define=TAGO_KEY (리포에 커밋하지 않음)
  메모리 캐시 30초      정류장별. 방향 토글 왕복 시 재호출 방지
  폴링 30초            오늘 탭이 살아있고 앱이 포그라운드일 때만
      │  https — ATS 예외 불필요
      ▼
[TAGO 1613000]  ArvlInfoInqireService / BusSttnInfoInqireService
```

### https는 실측으로 확인했다

기획 원본 8번의 curl 예시가 `http://`라 iOS ATS(App Transport Security) 예외와 심사 소명이
필요할 수 있었다. 이것이 프록시의 숨은 이득 중 하나였는데, **불필요함이 확인됐다**(2026-07-28).

```
subject: C=KR; O=National Information Society Agency; CN=*.data.go.kr
issuer:  GlobalSign RSA OV SSL CA 2018
SSL connection using TLSv1.3   ssl_verify_result=0
더미 키 요청 → HTTP 401        (TLS 정상, 키만 거부)
```

`Info.plist`에 ATS 예외를 넣지 않는다. 모든 요청은 `https://apis.data.go.kr`로 간다.

### 왜 지금은 서버를 두지 않는가

프록시의 논거는 셋이었고 둘이 무너졌다.

1. ~~한도~~ — 위 계산대로 앱 직접 호출로도 **약 500명**까지 버틴다. 지금 규모에서 한도는
   서버를 정당화하지 못한다.
2. ~~ATS 우회~~ — https 실측으로 비용이 0이 됐다.
3. **고칠 수 있는 속도** — 유일하게 남은 논거. 유효하지만 이것은 보험이고, 지금은 보험료가
   기능 자체보다 비싸다.

### 되살아나는 리스크와 완화 (수용)

| 리스크 | 앱 직접의 대가 | 완화 |
|---|---|---|
| 키 탈취 | 재발급 + 앱 수정 + **심사 1~3일**, 그동안 기능 정지 | 개발계정 키는 무료·즉시 재발급. 사용자가 적어 피해 규모도 작다 |
| 한도 관측 | 서버 대시보드가 없다 | data.go.kr 마이페이지의 일일 호출량을 릴리즈마다 눈으로 확인 (§5) |
| 폴링/TTL 조절 | 심사 뒤에 잠긴다 | 폴링 30초로 보수적으로 시작 — 조일 일은 없고 풀 일만 남게 |
| TAGO 응답 포맷 변경 | 구버전 사용자가 계속 깨진다 | 파서를 관용적으로 짠다 — 모르는 필드 무시, 결측 허용, 실패 시 빈 목록 |

### 키 관리

`--dart-define` 선례가 이미 있다 — `main.dart:13`의 `bool.fromEnvironment('SCREENSHOT_MODE')`.
같은 패턴으로 `String.fromEnvironment('TAGO_KEY')`를 쓴다.

- **리포에 커밋하지 않는다.** 로컬 보관은 리포 밖(`~/.planroutine/tago_key`).
- `Fastfile:272`의 `sh("flutter", "build", "ipa", ...)`에 `--dart-define=TAGO_KEY=#{key}`를
  추가하고, **키를 못 읽으면 레인을 실패시킨다.** 키 없이 빌드하면 기능이 조용히 죽은 앱이
  스토어에 올라간다 — 조용한 실패를 막는 가드다.
- **Decoding 키를 넣는다.** Dart `http`가 쿼리 파라미터를 인코딩하므로 Encoding 키를 넣으면
  이중 인코딩으로 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 난다(원본 8번 함정 1번).
- **난독화는 방어가 아니다.** 키는 IPA 안에 문자열로 남는다. `--dart-define`의 실질 가치는
  **git 히스토리에 남지 않는 것**이다 — 이 리포는 과거 실데이터를 히스토리에서 제거한 이력이 있다.

### 캐시와 경과 보정

서버가 없으니 Cloudflare KV의 60초 최소 TTL 제약이 사라졌다. 앱 메모리 캐시라 TTL이 자유롭다.

- 폴링 30초 = 호출 주기. 메모리 캐시 TTL도 30초로 맞춘다.
- 캐시의 역할은 둘이다 — **방향 토글로 왕복할 때**(30초 안에 출근↔퇴근을 오가면 두 번째부터
  캐시가 답한다), 그리고 **탭을 옮겼다 오늘 탭으로 돌아올 때**(빈 카드가 깜빡이지 않는다).
- 그래서 캐시는 `bus_api_client` 인스턴스가 들고, **client provider는 `autoDispose`가 아니다.**
  카드 provider만 autoDispose다. 둘 다 autoDispose로 두면 탭을 옮길 때마다 캐시가 사라져
  두 번째 역할을 못 한다. 대신 슬롯이 교체되면 캐시를 명시적으로 버린다(§6 push 함정 참조).
- 캐시 히트일 때 값이 최대 30초 묵으므로 **경과 보정**을 넣는다.

```dart
// bus_card_view.dart
final elapsed = now.difference(fetchedAt).inSeconds;
final displayMin = ((arrival.arrMin * 60 - elapsed) / 60).ceil();
```

"4분"으로 받은 값이 50초 묵었으면 화면에는 **3분**으로 나간다. 캐시가 30초 TTL이라 오차는
30초 이내지만, 보정은 폴링이 늦어졌을 때(백그라운드 복귀 직후 등)도 함께 지킨다.

### 프록시로 승격할 때 앱 변경이 작게 유지되도록 짠다

정규화·판정을 `data/tago_response_parser.dart`의 **순수 함수**로 분리한다. 프록시를 도입하면
이 파일이 서버로 그대로 옮겨가고, 앱에는 base URL 교체와 키 주입 제거만 남는다. 지금 이 분리를
해두지 않으면 승격 비용이 "다시 설계"가 된다.

## 3. 실패 계약 — 신뢰의 급소

원본 6번이 "명확한 빈 상태 문구 — 신뢰에 직결"이라고 짚은 것을 계약으로 못박는다.
**다섯 상태가 화면에서 서로 구분돼야 한다.**

| 상황 | 판정 근거 (실측 확인, 2026-07-28) | 카드 표시 |
|---|---|---|
| 정상 | `resultCode == '00'` + `items`가 Map(단건) 또는 List(복수) | 목록 + "07:32 기준" |
| 도착정보 없음 (막차 후 등) | `resultCode == '00'` + **`items == ""`**, `totalCount == 0` | "오늘 운행이 끝났어요" |
| 네트워크/TAGO 장애 + 캐시 있음 | 예외 발생, 메모리 캐시 존재 | 캐시 목록 + "07:30 기준 (갱신 실패)" |
| 장애 + 캐시 없음 | 예외 발생, 캐시 없음 | "지금 정보를 못 받았어요 · 다시 시도" |
| **키 문제** | HTTP 401 또는 `resultCode != '00'` | "버스 정보를 불러올 수 없어요" + 로그 |

앞의 넷은 프록시 설계에도 있었다. **다섯째가 앱 직접 호출에서 새로 생긴다** — 서버가 없으니
키 오류가 사용자 화면까지 도달한다. 사용자에게 키 이야기를 하지 않는다(할 수 있는 일이 없다).
개발자가 알아채는 경로는 로그와 §5의 호출량 점검이다.

빈 결과와 장애를 같은 문구로 뭉개면 사용자가 "막차 끝남"과 "앱 고장"을 구별할 수 없다.
버스 앱에서 이 둘의 차이는 **정류장에서 기다릴지 택시를 부를지**를 가른다.

> ⚠️ **`resultCode '03'`(NODATA)은 관측되지 않았다.** 앞선 리비전이 그것을 빈 상태 판정
> 근거로 적었는데 **추정이었고 틀렸다.** 실제 TAGO는 데이터가 없어도 `resultCode "00"`을
> 주고 `items`를 **빈 문자열 `""`** 로 준다(Map도 List도 아니다). `resultCode`로 판정하면
> 막차 후에 "운행이 끝났어요"가 뜨지 않고, `items['item']`으로 바로 들어가면 String에
> 인덱스 접근이라 **파싱이 깨진다.**

> ⚠️ **잘못된 `cityCode`도 똑같은 빈 응답이 온다.** `cityCode=99999`로 찔러도 오류가 아니라
> `items: ""`다. 즉 **API는 도시를 잘못 골랐다고 알려주지 않는다** — 사용자에게는 "오늘 운행이
> 끝났어요"로 보인다. §4의 확인 시트가 필요한 또 하나의 근거다.

### 정규화 (`tago_response_parser.dart`, 순수 함수)

실측으로 확인한 응답 형태를 그대로 받는다.

- **`items`가 세 형태로 온다**: `Map`(단건) · `List`(복수) · `""`(없음). 셋을 모두 받아
  `List<BusArrival>`로 정규화한다. 빈 문자열을 빈 목록으로 바꾸는 것이 빈 상태 판정이다.
- **`routeno`는 `int`와 `String`이 섞여 온다** — `92`(int) / `"92-1"`(String). 하이픈이 있는
  노선번호만 문자열이다. **반드시 `.toString()`으로 받는다.** `as String` 캐스트는 숫자
  노선번호에서 크래시한다.
- **같은 노선이 여러 건 온다** — 다음 차와 그다음 차가 별 항목이다. 실측: 고유 노선 5개에
  항목 10개. **`routeid`별로 `arrtime`이 가장 작은 것만 남긴다.** 축약하지 않으면 카드에
  `92번 10분 · 92번 25분`이 나란히 떠 같은 노선이 두 줄을 쓴다.
- `arrtime`(초) → `arrMin`: `ceil(sec / 60)`, 0이면 "곧 도착"
- 축약 후 `arrtime` 오름차순 정렬
- `vehicletp == '저상버스'` → `lowFloor` bool
- `citycode`·`nodeno`·`arrprevstationcnt`는 `int`로 온다. `nodeno`는 `2251` 같은 4자리이고
  하이픈 형식이 아니다.
- 모르는 필드는 무시하고, 결측 필드는 null로 받는다 (포맷 변경 내성)

## 4. 정류장 등록 — 방향이 조용히 틀리는 것을 막는다

**TAGO `nodeId`는 방향별로 별개다.** "시청앞" 한 곳이 아니라 상행 정류장 / 하행 정류장이 각각
다른 ID를 갖는다. 길 건너 마주보는 두 정류장이 같은 이름이다. 잘못 고르면 화면에는 버스가 정상적으로
뜨지만 **전부 반대 방향**이다 — 사용자는 앱이 고장 났다고 생각하지 않고 자기가 늦었다고 생각한다.

실측으로 확인했다(수원시 `31010`, `nodeNm=시청`):

```
GGB201000156  수원시청.수원일자리센터  (37.2622667, 127.0283833)
GGB202000003  수원시청.수원일자리센터  (37.2628167, 127.0279000)
```

**이름이 완전히 같고 좌표 차이는 약 60m다.** 이름으로도 좌표로도 사람이 고를 수 없다.
같은 검색어에 23건이 나왔고 그중 `수원시청역N번출구` 계열까지 섞인다.

### 저장 직전 확인 시트

정류장을 탭하면 바로 저장하지 않고, 그 정류장에 실제로 오는 버스를 한 번 조회해 보여준다.

```
┌───────────────────────────────────┐
│  이 정류장이 맞나요?                │
│  수원시청.수원일자리센터  2251       │
│                                   │
│  타는 버스만 남겨주세요              │
│   ☑ 82-1번    8분 후               │
│   ☑ 92번      10분 후              │
│   ☑ 92-1번    10분 후              │
│   ☑ 81번      13분 후              │
│   ☑ 61번      31분 후              │
│                                   │
│      [ 아니에요 ]    [ 맞아요 ]     │
└───────────────────────────────────┘
```

정류소번호는 `2251` 같은 **4자리 정수**다(실측). 앞선 리비전이 `12-345` 형식을 예로 들었는데
경기도는 하이픈을 쓰지 않는다.

### 노선 선택은 같은 시트에서 한다 — 단계가 늘지 않는다

원본 기획 3번 표의 `routeid | 노선 고유 ID | 등록한 버스 필터링`이 이것이다(앞선 리비전이
빠뜨렸다). 실측하니 정류장 하나에 노선이 **5개**였고 도심 거점은 더 많다 — 필터가 없으면
카드가 남의 버스로 채워진다.

**확인 시트가 이미 노선 목록을 그리고 있으므로 체크박스만 붙인다.** 방향 확인과 노선 선택이
같은 정보(노선 번호)를 근거로 하니 한 화면에서 끝난다.

- **기본은 전부 체크.** 방향만 확인하려는 사람이 `맞아요`만 눌러도 되게 — 확인 시트의 원래
  목적을 방해하지 않는다.
- 최소 1개는 남겨야 저장된다. 0개면 카드가 영구히 빈다.
- 노선을 바꾸려면 슬롯 타일을 다시 탭해 이 시트로 온다. 설정에 별도 항목을 두지 않는다.

### "전부"는 빈 집합으로 저장한다 — 미래 노선 때문이다

`BusStop.routeIds`에 무엇을 담는지가 나중에 갈린다.

| 사용자 상태 | 저장 | 새 노선이 생기면 |
|---|---|---|
| 전부 체크 | **`{}` (빈 집합 = 필터 없음)** | 자동으로 보인다 |
| 일부만 체크 | `{선택한 routeId들}` | 안 보인다 (의도한 대로) |

전부 체크된 상태를 `{5개 routeId}`로 저장하면 **"전부"가 "이 다섯 개"로 굳는다.** 노선이 신설되면
사용자는 전부를 골랐는데도 새 버스를 못 본다 — 몇 년 뒤 조용히 나타나고 원인을 찾기 어려운 종류다.
`{}`는 "지금 오는 것 전부"라는 뜻이라 시간이 지나도 뜻이 변하지 않는다.

방향은 좌표나 이름으로 사람이 판별할 수 없지만 **자기가 타는 버스 번호는 안다.** 노선 번호를
보여주면 사용자가 스스로 맞는 쪽을 고른다. 도착정보 조회 경로를 그대로 재사용한다.

### 검색 방식 — 이름 검색만

`getSttnNoList`(이름 검색)는 `cityCode`가 필수라 "도시 선택 → 정류장명" 2단이 된다.

**도시코드는 시·도가 아니라 시·군 단위다**(실측). 전국 138개이고 경기도만 `31010 수원시` ~
`31380 양평군` 31개다. 즉 "경기도"를 고르는 것이 아니라 "수원시"를 골라야 한다.

138개를 스크롤로 고르게 하면 초기 등록 마찰이 크므로 **도시 선택 화면에 검색 필드를 둔다** —
`수원`을 치면 좁혀진다. 목록은 `getCtyCodeList` 결과를 그대로 쓰고(`citycode`는 `int`),
마지막 선택을 저장해 교체할 때 다시 고르지 않는다.
`getCrdntPrxmtSttnList`(좌표 근접)는 위·경도만 받아 도시 선택을 우회하지만, **GPS는 교체
시나리오에서 못 쓴다** — 3월에 학교를 옮기면 새 학교 정류장을 집에서 등록하고, 이사하면 새 집
정류장을 이사 전 집에서 등록한다. 대상 정류장 근처에 없는 것이 교체의 기본값이다.

이름 검색만 넣는다. 새 의존성 0, 새 권한 0, 위치 권한 소명 0. 도시는 마지막 선택을 기억해 매번
고르지 않는다.

## 5. 한도 관측과 프록시 승격 조건

서버가 없으니 호출량을 자동으로 볼 수 없다. **수동 점검 지점을 정해둔다.**

- **점검 위치**: data.go.kr 마이페이지 → 오픈API → 활용 현황 (일일 호출량)
- **점검 시점**: 버스 기능이 포함된 릴리즈마다 + 이후 월 1회
- 이 절차를 `docs/release_checklist.md`에 한 줄 추가한다 — 기억에 의존하면 점검하지 않는다.

### 승격 조건 (하나라도 만족하면 프록시를 도입한다)

1. 일일 호출량이 **6,000회**(개발계정 10,000의 60%)를 넘긴 날이 관측된다.
2. 운영계정(100,000/일)으로 승격한 뒤에도 여유가 20% 미만이다.
3. 키 오용·탈취 징후가 있다(내가 쓰지 않는 시간대의 호출량, 급증).
4. TAGO 응답 포맷이 바뀌어 구버전 사용자가 깨지는 일이 실제로 발생한다.

승격 시 작업은 §2 마지막 항목대로 **`tago_response_parser.dart`를 서버로 이동 + base URL 교체**다.
그때 설계는 이 문서의 이전 리비전(git 히스토리)에 프록시 안으로 남아 있다 — Cloudflare Workers
+ KV 60초 + 무상태 + rate limit 안이다.

### 설정 탭

`SettingsSection(title: '버스 도착')` — **`완료 도장` 다음**에 놓는다. 둘 다 오늘 탭의 표시를
바꾸는 설정이라 붙여두면 찾기 쉽다.

- `표시` 스위치 (기본 OFF). subtitle은 `지정한 시간대에만 펼쳐집니다`
- ON일 때만 5줄:
  - `출발지 · 시청앞` / `도착지 · 학교앞` → 탭하면 `/bus/stops` push
  - `카드 모양 · 간단히` → 간단히 / 시간 축 (기본 `간단히`)
  - `출근 시간대 · 07:00 – 08:30` / `퇴근 시간대 · 16:00 – 18:00` → 시간 범위 피커

### 오늘 탭 배선 — `buildTodayView`는 건드리지 않는다

카드는 `today_body.dart` 최상단에 조건부로 들어가지만 `TodayView`에는 섞지 않는다.
`buildTodayView`는 업무 완료·진행도 계산 함수이고 버스는 그 도메인이 아니다. 섞으면 순수 함수
하나가 두 주제를 갖고 기존 테스트가 흔들린다. 카드는 별 provider를 watch하는 형제 위젯이다.
**기존 480개 테스트는 무손상이다.**

### CLAUDE.md의 push 함정이 여기 정확히 걸린다

> ⚠️ `push`는 예외다. `push`로 덮인 화면은 offstage로 마운트가 유지돼 autoDispose가 걸리지 않는다.
> **오늘 탭에 push 라우트를 붙이면** 그 화면이 리비전을 올리지 않는 한 pop 후 목록이 stale이 된다.

카드의 빈 상태에서 `/bus/stops`로 push하면 이 조건이 성립한다. 정류장을 바꿔 돌아왔는데 카드가
옛 정류장을 계속 폴링하는 버그가 된다.

대응: 저장 시 `shared_preferences` 쓰기와 **동시에 `busSettingsProvider` state를 갱신**하고, 카드는
그 provider를 watch해 슬롯이 바뀌면 메모리 캐시를 버리고 새 `nodeId`로 폴링을 재시작한다.
위젯 테스트로 고정한다.

### 요청이 나가는 조건 — 여섯 개가 모두 참일 때만

호출 예산은 이 목록이 지킨다. **하나라도 거짓이면 TAGO 요청은 0이다.** 조건을 여러 곳에 흩어
놓으면 새는 구멍이 생기므로 한곳에 모아둔다.

1. 설정 `표시`가 ON이다.
2. 그 방향의 정류장 슬롯이 설정돼 있다.
3. 카드가 **펼침** 상태다 (§1 — 시간대 밖이거나 사용자가 접었으면 거짓).
4. 오늘 탭이 화면에 있다 (provider가 살아 있다).
5. 앱이 **포그라운드**다.
6. 메모리 캐시가 미스다 (30초 경과).

**접힘이 요청 0인 근거는 3번 하나가 아니다** — 접힌 줄은 도착 분을 그리지 않으므로(§1) 조회한
데이터를 쓸 곳이 없다. 즉 접힘에서 요청이 나간다면 그것은 최적화 누락이 아니라 **버그**다.

### 요청을 촉발하는 지점 — 이 넷뿐

| 촉발 | 조건 |
|---|---|
| 30초 폴링 타이머 | 위 6개 |
| 접힘 → 펼침 전환 | 위 6개 (캐시가 살아 있으면 캐시로 즉시 그리고 요청 없음) |
| 포그라운드 복귀 | 위 6개 — **특히 3번.** 접힌 채 복귀하면 조회하지 않는다 |
| 슬롯 교체 · 방향 토글 | 위 6개. 캐시를 버리고 새 `nodeId`로 |

정류장 검색 화면과 확인 시트(§4)는 별개 경로다 — 거기서는 사용자의 검색·선택이 요청을 촉발한다.

### 폴링 수명

- 주기 30초. 백그라운드 진입 시 타이머 정지(`AppLifecycleListener`).
- 카드 provider는 `autoDispose` — `todayViewProvider`와 같은 이유다(이 앱은 `ShellRoute`라
  탭을 옮기면 화면이 dispose된다).

## 7. 개인정보

우리 서버가 없으니 우리가 수집하는 데이터는 0이다. 다만 앱이 **국토교통부 TAGO API로 직접
요청**하므로 정류장 ID와 기기 IP가 `data.go.kr`에 남는다.

이용자를 식별하는 정보를 전송하지 않으며, 별도 서버에 저장하지 않는다."

App Store 개인정보 설문의 "데이터 수집 없음"은 유지된다(우리가 수집하지 않는다).

## 10. 범위에서 뺀 것

원본 6번의 "넣지 말 것"을 그대로 유지한다.

- **길찾기·경로검색** — ODsay 영역, 무거움. 네이버지도가 할 일.
- **즐겨찾기 무한 등록** — 2슬롯으로 충분.
- **실시간 지도 버스 아이콘** — 호출량·복잡도 큼. "분"이면 충분.
- **푸시 알림** — 백그라운드 폴링이 필요해 서버·배터리 부담. 1단계 제외.
- **OS 홈화면 위젯** — 네이티브 WidgetKit 필요 + OS가 실시간 갱신을 극도로 제한해 버스 도착과
  상성이 나쁘다.
- **일정 장소 자동 버스 추천 / 출발시간 역산** — 원본 2단계. 길찾기 의존.
- **프록시 서버** — §5의 승격 조건을 만족하면 도입한다. 지금은 아니다.

원본 6번의 "여력되면" 항목 중 **저상버스 표시**(`vehicletp` → 아이콘 하나)는 Phase 3에서 여력이
있으면 넣고, 없으면 뺀다. 두 모양 모두 자리가 넉넉하지 않다 — `간단히`는 한 줄에 노선을 나열해
아이콘이 끼면 줄이 넘치고, `시간 축`은 축 아래 라벨이 이미 좁다. 넣는다면 `간단히`의 노선번호
뒤 한 곳만이고, 노선이 3개 이상이면 생략한다.

- **3구 신호등 안**(색·위치 두 채널, ≈92px) — 비교 후 미채택. 신호는 가장 강하지만 가장 높고
  색을 반드시 들여야 한다. 되살릴 이유가 생기면 `BusCardStyle`에 값을 하나 더 붙이면 된다.
- **링 게이지 안** — 미채택. 바로 아래 결산 링과 **같은 형태로 다른 뜻**(시간 vs 진행도)을 말하고,
  차오름의 의미까지 반대다(결산 링은 가득=완료, 게이지는 가득=도착 임박). 골드가 네 의미를 겸하지
  않도록 토요일을 파랑으로 뺐던 것과 같은 실수를 형태에서 반복하게 된다.
- **다음 버스 하나만 크게 보이는 안** — 미채택. 가장 빠르게 읽히고 가장 낮지만, 그 노선을 타지
  않는 사람이 매번 작은 줄을 읽어야 한다. 정류장에 노선이 둘 이상이면 손해가 크다.
