# 아이폰 단축어 연계 — 앱 타깃 App Intents

**2026-09-13**

## 개요

공직플랜을 외부 AI 앱과 잇는다. 지금은 `① 프롬프트 복사 → AI 앱 → ② 붙여넣기`라는
클립보드 왕복이 유일한 통로인데, 여기에 **단축어라는 두 번째 통로**를 낸다. 노출하는 것은
**일정 등록**과 **일정 조회** 두 가지이고, 둘 다 **앱을 열지 않고** 동작한다.

핵심 결정은 **패키지를 쓰지 않고 인텐트를 앱 타깃에 직접 두는 것**이다. 이 결정이
App Group·데이터베이스 이전·스키마 이중화를 전부 없앤다. 근거는 추측이 아니라 실측이며
아래 "실험으로 확정한 것"에 적는다. 실험 기록 원본은 `.local/experiments/`에 있다(git 제외).

Swift는 **인텐트를 선언하고 채널을 부르는 일만** 한다. 파싱·중복 체크·삽입은 전부 기존
Dart 코드가 그대로 진다. 이 경계가 설계의 중심이고, 이것이 무너지면 스키마 지식이 두 곳으로
갈라져 이 저장소가 여러 번 겪은 부류의 결함이 돌아온다.

## 실험으로 확정한 것

시뮬레이터(iPhone 17 / iOS 26)에서 앱을 완전히 종료한 뒤 단축어로 인텐트를 실행해 관측했다.

| 관측 | 결과 |
|---|---|
| 앱이 전면에 뜨는가 | **뜨지 않는다.** 화면은 단축어 앱 그대로였다 |
| 어느 프로세스에서 도는가 | **앱 프로세스**(`processName: Runner`, 앱 번들 ID, 앱 Documents) |
| `AppDelegate`가 도는가 | **돈다.** `didFinishLaunchingWithOptions` 호출 확인 |
| Dart가 실행되는가 | **된다.** `main()` 실행과 핸들러 등록까지 확인 |
| Dart를 부를 수 있는가 | **부를 수 있다.** MethodChannel로 `pong from dart`가 왕복했다 |
| 기동부터 응답까지 | **약 2초** (10:44:03 → 10:44:05) |

**초기 진단이 틀렸던 지점을 적어 둔다.** "Flutter라서 App Intents에서 Dart를 못 쓴다"고
판단했고 근거는 flutter/flutter#152799가 열려 있다는 것이었다. 그 이슈가 말하는 것은
**App Extension**(위젯 확장 등)에서의 Dart 실행이고, 거기는 엔진을 띄울 수 없는 것이 맞다.
**인텐트를 앱 타깃에 두면 확장이 아니라 앱이 뜬다.** `app_intents`·`flutter_app_intents`
두 패키지가 `openAppWhenRun = true`를 박은 것도 플랫폼 제약이 아니라 패키지의 선택이었다 —
명시하지 않으면 빌드 산출물(`Metadata.appintents/extract.actionsdata`)에
`"openAppWhenRun":false`로 기록된다.

## 아키텍처

### 경계가 설계다

```
단축어 / 시리
    │
    ▼
[Swift] RegisterSchedulesIntent · QuerySchedulesIntent
    │      ├ 인텐트 선언(제목·파라미터·반환)
    │      └ 채널 호출 + 대기/타임아웃
    │      ※ 파싱·중복체크·SQL 없음
    ▼  MethodChannel "planroutine/app_intents"
[Dart] AppIntentsHandler
    │      └ 기존 코드로 위임만 한다
    ▼
parseAiScheduleJson · ScheduleRepository · CalendarRepository
```

**Swift에 비즈니스 로직을 두지 않는다.** 규칙이 아니라 구조로 지킨다 — Swift가 아는 것은
채널 이름과 메서드 이름뿐이고, 테이블·컬럼·상태값은 하나도 모른다. 스키마를 v9로 올려도
Swift는 손대지 않는다.

### 노출하는 것 둘

**`일정 등록`(RegisterSchedulesIntent)**

- 입력: 텍스트 한 덩어리, 종류(업무/행사). **기본값은 행사** — 사진 AI 경로의 히어로
  세그먼트와 같은 기본값이고, 단축어로 넘어오는 것도 대개 AI가 일정표에서 뽑은 행사다
- 처리: `parseAiScheduleJson` → `insertConfirmedOrPending`(중복 체크 포함) → 검토 대기로 적재
- 반환: `등록 N건 · 중복 M건 제외` 형태의 한 줄
- **AI 앱의 답변을 그대로 넘기면 된다.** 지금 클립보드에 붙여넣는 그 형식이고, 파서를
  재사용하므로 형식 규칙이 한 곳에만 있다.

**`일정 조회`(QuerySchedulesIntent)**

- 입력: 기간(오늘 / 이번 주 / 이번 달)
- 처리: `getEventsByDateRange` → 사람이 읽는 텍스트로 조립
- 반환: 텍스트. 단축어가 이것을 AI 앱에 넘기거나 알림으로 띄운다

**엔티티(`AppEntity`)를 만들지 않는다.** 조회를 인텐트로 두면 앱을 열지 않으면서도 Dart가
답하므로 엔티티가 주는 이점(캐시로 콜드 스타트 응답)이 필요 없다. 엔티티는 캐시 동기화라는
두 번째 진실 공급원을 만드는데, 지금 구조에서는 그 비용만 남는다.

**완료 체크와 일괄 확정은 범위 밖이다.** 요청이 등록과 조회였고, 완료 처리는 오늘 탭의
도장 애니메이션이 의미의 절반이라 단축어로 옮기면 그 절반이 사라진다.

### Dart 준비를 기다리는 장치

⚠️ **이것이 설계에서 가장 조심할 지점이다.**

실험에서 Dart `main()`이 인텐트 `perform()`보다 1초 먼저 도달했지만, **그 순서가 보장인지는
확인되지 않았다**(1회 관측). 뒤집히면 채널 호출이 무응답이 되고 인텐트가 조용히 실패한다.

그래서 **순서를 우연에 맡기지 않는다.**

- Dart가 핸들러 등록을 마치면 채널로 `ready`를 보낸다.
- Swift는 그 신호를 받을 때까지 기다린다. 이미 받았으면 즉시 통과한다.
- **상한은 5초다.** 실험에서 기동부터 Dart 준비까지 약 1초였고(10:44:03 → 10:44:04),
  인텐트 전체가 시스템에서 받는 시간이 약 30초이므로 그 안에 넉넉히 든다.
- 상한을 넘기면 **실패를 말한다.** 조용히 빈 결과를 돌려주지 않는다 — 사용자가 "등록됐다"고
  믿는 것이 가장 나쁜 결과다.

### 앱이 이미 떠 있을 때 화면을 갱신한다

인텐트가 앱 프로세스에서 돌므로, 앱이 포그라운드일 때 단축어로 등록하면 **같은 프로세스의
Riverpod 상태를 그대로 만진다.** 등록 후 `eventsRevisionProvider`를 올리지 않으면 화면이
그대로라 사용자에게는 실패로 보인다.

이미 있는 신호 체계를 그대로 쓴다. 캘린더 CRUD가 올리는 그 리비전이고, 오늘 탭이 watch한다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| Dart 준비보다 인텐트가 먼저 도달 | `ready` 신호 대기 + 상한 + 실패 문구 (위 절) |
| 앱이 꺼져 있을 때 약 2초 지연 | 받아들인다. 단축어가 기다리는 시간이며 줄일 수단이 없다 |
| 실기기 미검증 | **남은 항목.** 시뮬레이터에서는 수동 `codesign`으로 서명을 맞췄다 |
| `AppShortcutsProvider` 추출 누락 | 증분 빌드에서 1회 관측. 재발하면 클린 빌드로 확인 |
| 채널 이름이 Swift와 Dart 두 곳에 | **유일한 이중화.** 가드 테스트로 묶는다 (아래) |
| 배포 타깃 상향(13.0 → 16.0) | 사용자 승인 완료. 되돌릴 수 없다 |

## 테스트 전략

**Dart 쪽은 평소대로 단위 테스트를 쓴다.** 채널 핸들러가 얇으므로(위임만 한다) 검사할 것은
"인자를 옳게 풀어 기존 함수에 넘기는가"와 "결과 문구를 옳게 조립하는가"이다.

**Swift 쪽은 위젯 테스트로 밟을 수 없으므로 소스를 검사한다.** 이 저장소가 안드로이드 알림
배선에서 이미 쓴 방법이다(`android_wiring_test.dart` 15건).

가드가 잡아야 하는 것:

1. **채널 이름과 메서드 이름이 Swift와 Dart에서 같은가** — 양방향으로 본다. 한쪽만 고치면 깨진다.
2. **`openAppWhenRun`을 `true`로 되돌리지 않았는가** — 이 한 줄이 설계 전체의 전제다.
   누군가 "앱이 열려야 결과가 보이지" 하고 바꾸면 조용히 원래 문제로 돌아간다.
3. **Swift에 SQL이나 테이블 이름이 등장하지 않는가** — 경계가 무너지는 순간을 잡는다.
4. **배포 타깃이 16.0 이상인가** — 낮추면 인텐트가 빌드에서 조용히 빠진다.

## 구현 순서

1. iOS 배포 타깃을 16.0으로 올리고 빌드가 통과하는지 확인한다.
2. Dart에 `AppIntentsHandler`와 채널을 배선하고 `ready` 신호를 보낸다. 단위 테스트를 먼저 쓴다.
3. Swift에 두 인텐트와 `AppShortcutsProvider`를 넣는다. `openAppWhenRun`은 쓰지 않는다.
4. 가드 테스트 네 종을 추가한다.
5. 시뮬레이터에서 앱을 끈 상태로 두 인텐트를 실행해 동작을 확인한다.
6. TestFlight에 올려 **실기기에서 확인한다**(시뮬레이터가 못 보는 서명·프로비저닝 조건).

## 범위 밖

- 안드로이드 AppFunctions. Android 16 이상에서만 동작하고(점유율 25.2퍼센트) 제미나이 연동이
  비공개 미리보기라 지금 착수하지 않는다. 조기 접근 프로그램 신청만 해 둔다.
- 원격 MCP 서버. 계정 체계·서버 저장소·동기화·OAuth 2.1이 전부 새로 필요하고 개인정보
  처리방침의 근거가 무너진다. 조사 결과는 옵시디언 노트에 있다.
- 구글 캘린더 양방향화. 앱이 호출 대상이 되지 않아 연계라 부르기 어렵다는 판단으로 기각했다.
