# 제목 연도 +1 이동 + 가져온 자료 `작년` 배지 — 설계

## 개요

에듀파인 CSV로 작년 업무를 가져오면 날짜만 올해로 바뀌고 **제목의 연도는 원본 그대로** 남는다.
지금은 "올해보다 이전 연도를 올해로 맞추는" 규칙이라 `2025학년도 …`만 잡히고 `2026 졸업식 …`은
그냥 통과한다. 실제로는 둘 다 한 해 밀려야 한다.

두 가지를 바꾼다.

1. **캘린더 목록에 `작년` 배지** — 가져온 항목임을 알리는 **출처 표시**. 제목에 연도가 없어도 붙는다.
2. **편집 화면의 연도 칩을 `+1년`으로** — `2025 → 2026`, `2026 → 2027`. 목록의 골드 연도 배지는 없앤다.

## 배경 — 지금 무엇이 안 되는가

`title_year_utils.dart:20`이 이렇게 걸러낸다.

```dart
if (year < currentYear) { ... }   // 올해 이상은 "이미 미래 참조"로 보존
```

2026년에 작년 자료를 가져오면:

| 제목 | 지금 | 있어야 할 값 |
|---|---|---|
| `2025학년도 재학생 진급 …` | `2026학년도 …` ✓ | `2026학년도 …` |
| `2026 졸업식 행사 관련 협의` | **그대로** ✗ | `2027 졸업식 …` |
| `종업식 및 졸업식 학사일정변경 안내장` | 그대로 ✓ | 그대로 |

`2026 졸업식`이 통과하는 이유는 규칙이 "미래 참조는 보존"이기 때문인데, 이건 미래 참조가 아니다.
**12월 업무가 두 달 뒤(2월) 졸업식을 가리킨 것**이라, 날짜가 한 해 밀리면 가리키는 졸업식도
한 해 밀린다.

### 절대 기준이 관계를 뭉갠다

기존 테스트가 이 문제를 이미 담고 있다(`title_year_utils_test.dart:36`).

```
입력:      2025학년도 안건발의서[2026학년도 보결수업 규정 개정]
지금:      2026학년도 안건발의서[2026학년도 …]   ← 둘 다 2026, 관계 소실
+1년:      2026학년도 안건발의서[2027학년도 …]   ← "올해 발의한 내년 규정" 유지
```

"올해로 맞춘다"는 **절대** 기준이라 서로 다른 두 연도를 같은 값으로 뭉갠다. "한 해 민다"는
**상대** 기준은 간격을 보존한다.

### `<`를 `<=`로 바꾸면 안 되는 이유

가장 작은 변경처럼 보이지만 끝나지 않는다. `2025 → 2026`을 눌러 고치는 순간 그 제목은
`2026`을 담게 되고, 같은 규칙이 다시 `2026 → 2027`을 제안한다. 한 번 처리해도 계속 조른다.

그래서 **조르는 쪽(목록 배지)과 고치는 쪽(편집 칩)의 기준을 분리한다.** 목록 배지는 출처만
말하고 연도를 보지 않으므로 반복될 여지가 없다. 편집 칩은 사용자가 일부러 연 화면에만 있어
몇 번 눌리든 상관없다.

## 1. 목록 배지 — `작년`

에듀파인 CSV에서 온 항목에만 붙는 **출처 표시**. 연도가 없는 제목에도 붙는다.

```
┃ [업무] ★ 2025학년도 재학생 진급 …          [작년] [✓]
┃ [업무]   종업식 및 졸업식 학사일정변경 …    [작년]
┃ [업무]   손으로 넣은 항목                          ← 배지 없음
```

- **판정 기준**: `schedules.source_id != null`. CSV 경로(`ScheduleRepository.createFromImported`,
  `:48`·`:112`)만 이 값을 채운다. 사진 AI(`registerAiSchedules`)와 손입력은 비어 있다.
- **위치**: 지금 골드 연도 배지가 있던 행 오른쪽.
- **스타일**: **테두리만 있는 pill**(배경 없음), 10px w700, `AppColors.sub`.
  `KindBadge`와 같은 채움형으로 하면 `[업무]`(회색 채움)와 `[작년]`(회색 채움)이 같은 행에서
  구분되지 않는다 — 종류는 채움, 출처는 테두리로 형태를 갈라야 한 눈에 읽힌다.
  골드는 오늘·중요 전용이고, 이제 누르는 것도 아니라 강조할 이유가 없다.
- **문구는 `작년` 고정.** 2027년에 보면 재작년 자료도 `작년`이라고 말하는 부정확함이 있지만,
  출처 연도를 저장하려면 스키마가 늘어난다. 간단한 쪽을 택했다(사용자 확인, 2026-07-26).

### 데이터 경로 — 스키마 변경 없음

`calendar_events`에는 `schedule_id`만 있고 `source_id`가 없다. 컬럼을 늘리는 대신
`CalendarRepository.getEventsByDateRange`를 `rawQuery`로 바꿔 조인한다.

```sql
SELECT e.*, (s.source_id IS NOT NULL) AS from_import
FROM calendar_events e
LEFT JOIN schedules s ON s.id = e.schedule_id
WHERE e.event_date >= ? AND e.event_date <= ? AND e.deleted_at IS NULL
ORDER BY e.event_date ASC, e.created_at ASC
```

- **`CalendarEvent.fromImport`는 읽기 전용 파생 필드다.** `fromMap`에서만 채우고
  **`toMap()`에는 넣지 않는다** — 넣으면 `from_import` 컬럼이 없는 테이블에 insert가 깨진다.
  가드 테스트로 고정한다.
- 조인 결과가 없는 경로(`fromMap`을 쓰는 휴지통 등)는 키가 없어 `null` → `false`. 안전하다.
- 진실은 `schedules.source_id` 한 곳에만 둔다. 컬럼으로 복제하면 어긋날 여지가 생긴다.

### 범위

**캘린더 목록만.** 오늘 탭은 오늘 할 일을 하는 화면이라 출처가 방해되고, 입력 탭 검토 목록은
이미 종류·카테고리 배지가 있어 셋째는 과하다.

## 2. 편집 칩 — `연도 +1`

제목에 연도가 있으면 **항상** 뜬다. 편집 화면은 사용자가 일부러 연 곳이라 조를 걱정이 없다.

```
┌──────────────────────────┐
│ 2026 졸업식 행사 관련 협의 │
└──────────────────────────┘
  [ ⟳ 2026 → 2027 ]
```

- **연도 하나**: `2025 → 2026`처럼 실제 값을 보여준다.
- **연도 둘 이상**: `연도 모두 +1년`. `2025 → 2026`만 쓰면 뒤쪽 연도에 대해 거짓말이 된다.
- 여러 번 눌러도 된다 — 두 해 전 자료면 두 번. 한 번에 맞추는 규칙(가장 이른 연도를 올해로)은
  `2020년 개교 이래 … 2025학년도` 같은 제목에서 역사적 연도까지 크게 밀어버려 기각했다.
- 노출 위치는 지금과 같다: 제목 필드 바로 아래, 컨트롤러를 구독해 입력 중 실시간 갱신.

## 3. 순수 함수 — `shiftTitleYears`

```dart
// lib/core/utils/title_year_utils.dart
({String title, List<int> from}) shiftTitleYears(String title, {int by = 1})
```

- **이름을 바꾼다.** `bumpTitleYear(title, currentYear)`는 "올해로 맞춘다"는 절대 기준이었다.
  새 규칙은 상대 기준이라 이름을 그대로 두면 다음 사람이 옛 의미로 읽는다.
- `currentYear` 인자가 사라진다. 이제 올해가 무엇인지 알 필요가 없다.
- 정규식 `(?<!\d)20\d\d(?!\d)`는 그대로 — 문서번호(`문서120250`)·`1000명` 차단이 계속 유효하다.
- 반환의 `from`은 **중복을 제거한, 등장 순서대로의 원본 연도 목록**. `2025 … 2025`처럼 같은
  연도가 두 번 나와도 `[2025]` 하나다 — 라벨이 "연도 모두"로 넘어가지 않게 하려면 개수가
  distinct여야 한다. 연도가 없으면 빈 리스트.
- UI는 이 길이로 라벨을 고른다:
  - 1개 → `${from.first} → ${from.first + by}` (예: `2026 → 2027`)
  - 2개 이상 → `CalendarStrings.yearShiftAll` = `'연도 모두 +1년'`
  - 치환 자체는 길이와 무관하게 **모든 연도**에 적용된다.

## 4. 없어지는 것

- `event_list_section._buildYearBadge` — 목록의 골드 `2025→2026` 배지. 연도 바꾸기가 편집
  전용이 되므로(사용자 확인, 2026-07-26).
- `EventListSection.onEventBumpYear` 콜백과 `calendar_screen._onBumpYear` 핸들러.
- `event_list_section._goldPill` — 중요 배지(직전 작업에서 제거)와 연도 배지가 둘 다
  사라져 쓰는 곳이 없어진다.
- 목록에서 편집으로 가는 길은 **행 탭** 그대로다.

## 5. 테스트

**`test/core/utils/title_year_utils_test.dart` 전면 개정** — 기존 10건이 전부 "올해로" 기준이라
+1 기준으로 다시 쓴다(삭제가 아니라 개정).
- `2025학년도 겨울방학 운영 계획` → `2026학년도 …`, `from == [2025]`
- `2026 졸업식 행사 협의` → `2027 졸업식 …`, `from == [2026]` (지금은 안 바뀌는 케이스)
- `2024학년도 결산 2026` → `2025학년도 결산 2027`, `from == [2024, 2026]`
- `2025학년도 안건발의서[2026학년도 …]` → `2026학년도 안건발의서[2027학년도 …]` — 간격 보존
- 연도 없는 제목 → 그대로, `from`은 빈 리스트
- `1000명 참가 행사 계획` · `문서120250 처리` → 그대로 (비연도 차단 유지)
- `by: 2`를 주면 두 해 민다
- 같은 연도가 두 번 나오면 `from`은 중복 없이 1개 (`2025 상반기 2025 하반기` → `from == [2025]`,
  제목은 둘 다 2026으로)

**캘린더 목록** (`event_list_year_badge_test.dart` 개정 — 골드 연도 배지가 사라지므로)
- CSV 출처(`fromImport: true`) 이벤트에 `작년` 배지, 손입력에는 없음
- 연도 없는 제목의 CSV 출처 이벤트에도 `작년` 배지가 붙는다
- 골드 연도 배지와 `_goldPill`이 더 이상 렌더되지 않는다

**리포지토리**
- `getEventsByDateRange`가 CSV 출처 이벤트에 `fromImport == true`, 손입력에 `false`를 준다
- **`toMap()`에 `from_import` 키가 없다** — 이 가드가 insert 파손을 막는다

**편집 시트** (`event_edit_dialog_year_test.dart` 개정)
- 연도 1개: 칩 문구가 `2026 → 2027`, 탭하면 제목이 바뀐다
- 연도 2개: 칩 문구가 `연도 모두 +1년`, 탭하면 **둘 다** +1
- 연도 없음: 칩 미노출
- 두 번 탭하면 두 해 밀린다

## 범위 밖 (YAGNI)

- **출처 연도 저장**(`2025 자료` 같은 배지) — 스키마가 늘어난다. `작년` 고정으로 간다.
- **가져올 때 제목 연도 자동 치환** — 사용자가 보고 누르는 흐름을 원한다.
- 입력 탭 검토 목록·오늘 탭의 `작년` 배지.
- 사진 AI로 들어온 학교일정의 연도 처리 — 그쪽은 올해 일정표를 찍는 것이라 옛 연도가 없다.
- `schedules.title`의 연도 수정(캘린더 이벤트만 바꾼다) — 역방향 동기화는 이 앱의 방향이 아니다.

## 설계 근거

- **조르는 쪽과 고치는 쪽의 기준을 분리한 것**이 이 설계의 핵심이다. 하나의 규칙으로 둘을
  다 하려 하면(`<`를 `<=`로) 고칠수록 다시 조르는 순환에 빠진다. 목록 배지는 출처만 보고,
  편집 칩은 연도만 본다.
- **절대 기준 → 상대 기준.** "올해로 맞춘다"가 한 제목 안의 서로 다른 연도를 뭉갠다는 것이
  기존 테스트에 이미 증거로 남아 있었다. 한 해씩 미는 쪽이 자료의 내부 관계를 지킨다.
- **조인이지 컬럼이 아니다.** 출처는 `schedules.source_id`가 이미 알고 있다. 복제하면
  어긋날 수 있고, 마이그레이션도 는다. 읽기 시점 조인이면 진실이 한 곳에 남는다.
