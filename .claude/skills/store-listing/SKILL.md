# 스토어 등록정보 점검

Play가 `versionCode 143`을 거부한 곳은 바이너리가 아니라 **문안**이었다
(`혼동을 야기하는 주장 관련 정책 위반 — 정부 정보의 출처 링크 누락`). 그때 필요한 것은
새 빌드가 아니라 등록정보 수정이었다.

## 가드가 이미 보는 것 / 이 스킬이 보는 것

| 이미 기계가 본다 (`test/deploy/store_listing_credit_test.dart`) | 이 스킬이 본다 |
|---|---|
| 면책 주장 셋의 존재 | URL이 **지금도 200인지**(네트워크) |
| 데이터셋 URL 넷 + 포털 + 법령의 존재 | 문안 동기화 — 새 기능이 한쪽에만 있는지 |
| 두 문서의 URL 집합 일치 | 기준 버전 표기를 올릴 때인지(**판단**) |
| 기관 표 ↔ 실제 호출 양방향 | 릴리즈 노트·스크린샷 상태 |

**기계 검사를 먼저 돌린다.** 거기서 깨지면 이 스킬을 계속하지 말고 그것부터 고친다.

## 절차

### 0. 현재 상태

```bash
grep '^version:' pubspec.yaml
grep -h '기준 버전' docs/app_store_description.md docs/play_store_description.md
ls docs/release_notes/
```

> ⚠️ 스킬 본문에는 **동적 주입 문법**(느낌표 뒤에 백틱으로 명령을 감싸는 형태)을
> 예시로도 적지 말 것. 로더가 원문을 훑어 **그 자리에서 실행한다** — 마크다운
> 코드스팬으로 감싸도 막히지 않는다(실측 2026-08-13: 이 자리에 설명으로 적어둔
> 예시가 실행돼 `command not found: cmd`로 스킬 실행이 실패했다).
>
> 그래서 이 세 줄은 주입이 아니라 명령으로 둔다. 주입은 **읽기만 할 때도** 매번
> 실행되므로, 세 줄을 아끼려고 쓸 이유가 없다.

### 1. 기계 검사

```bash
flutter test test/deploy
```

### 2. URL 생존 확인

```bash
grep -o 'https://[^ )]*' docs/play_store_description.md | sort -u | while IFS= read -r u; do
  code=$(curl -s -o /dev/null -w '%{http_code}' -L --max-time 15 -A 'Mozilla/5.0' "$u")
  printf '  %-52s %s\n' "$u" "$code"
done
```

- ⚠️ **`for u in $urls`로 쓰지 말 것.** 이 환경의 셸은 zsh이고, zsh는 인용 없는 확장을
  **단어 분리하지 않는다** — 루프가 한 번만 돌고 URL 전체가 한 덩어리로 curl에 들어가
  `000`이 뜬다(실측). `while read`로 받는다.
- `-L`(리다이렉트)과 User-Agent가 둘 다 필요하다. 정부 사이트는 기본 UA를 막는 경우가 있다.
- **실측 기준선(2026-08-13): 7개 전부 200.** Play 문서는 개인정보처리방침 URL을 포함해
  7개, App Store 문서는 6개다 — **정상적인 비대칭**이다(ASC는 방침 URL을 메타데이터
  필드로 받는다). 가드는 출처 절만 비교하므로 이 차이에 걸리지 않는다.

### 3. 두 문서 문안 동기화 — 여기가 판단이다

- **기능 절**: 새 기능이 한쪽에만 적혀 있지 않은가(1.3.0에서 실제로 그랬다 — Play에만 있었다)
- **개인정보 절**: "기기 안에만"류 표현이 실제 동작과 맞는가. **버스 카드를 켜면 정류장
  조회가 기기에서 나간다** — 이 문장을 빼면 거짓이 된다
- **면책조항이 두 곳에 있는가**(도입부 + 전용 절). Play의 "쉽게 확인할 수 있도록" 요건이고,
  앱 이름이 `공직플랜`이라 정부 앱으로 오인될 여지가 있어 한 곳으로 줄이지 않는다
- **기준 버전 표기**: pubspec과 다를 수 있다(지금 문안 1.3.0 / pubspec 1.3.1).
  **자동으로 맞추지 않는다** — 이 표기는 "이 문안이 설명하는 기능 집합"이라 패치마다
  올릴 이유가 없다. 새 기능이 문안에 들어갔을 때만 올린다
- ⚠️ **에듀파인을 링크하지 않는다.** 앱은 에듀파인에 접속하지 않고 사용자가 고른 사용자
  본인의 파일을 읽을 뿐이다. 링크를 붙이면 "정부 시스템과 연동된다"는 오해를 만들어
  **같은 정책을 더 위반하는 쪽**으로 간다

### 4. 릴리즈 노트

- iOS: `docs/release_notes/<버전>.ko.txt` — 없으면 `release` 레인의 가드 E가 막는다
- Android: `<버전>-android.ko.txt`가 있으면 그것을 먼저 쓰고, 없으면 iOS 문안이 그대로
  테스터에게 간다. **그게 틀린 말일 수 있다** — 릴리즈 노트는 14일 opt-in 안내가 테스터에게
  자동으로 닿는 유일한 채널이다(이메일은 사람이 매번 기억해야 한다)

### 5. 스크린샷

```bash
./ios/bin/fastlane.sh asc_state
```

**장수만** 알려준다(`ko / APP_IPHONE_65 6장`). 파일명·순서는 ASC 웹에서 직접 봐야 한다 —
로컬에서 "어느 장이 빠졌는지"는 판정할 수 없다. 제출 후 장수가 줄어든 실측 사례가 있다.
슬롯마다 장수가 달라도 **다음 릴리스에서 맞추는 편이 값싸다** — 갈아치우려면
`withdraw_review`가 필요해 심사 대기열 처음으로 돌아간다.

## 보고

1. **URL**: n/n 200 (실패한 것은 URL과 코드를 함께)
2. **기계 검사**: `test/deploy` n건 결과
3. **판단 항목**: 어긋난 것만 — 무엇이 / 어디서 / 제안
4. 이상 없으면 그렇게 말한다. 없는 문제를 만들지 않는다

⚠️ **문안 수정은 사용자 확인 후에 한다.** `release` 레인이 스토어 설명을 실제로 업로드하므로
이 파일들은 외부로 나가는 콘텐츠다. 오탈자 하나도 제출물이 바뀐다.
